= 模块 2：工作负载注册与 X.509-SVID
:navtitle: 模块 2：工作负载注册

本模块回答的客户问题：*我的 Pod 如何获得一个加密身份，而无需在 Deployment 里硬编码任何证书或密钥？*

你将在自己的命名空间部署一个测试 Pod，创建 SpiffeClusterSPIFFEID 注册条目，然后检查 CSI Driver 挂载到 Pod 中的 X.509-SVID 内容。

.刚接触工作负载注册？
[%collapsible]
====
* *SpiffeClusterSPIFFEID* — 集群范围的 SPIFFE ID 注册条目，通过 Kubernetes 选择器（namespace + ServiceAccount）匹配工作负载。
* *X.509-SVID* — 包含 SPIFFE URI SAN 的 X.509 证书，私钥由 SPIRE Agent 在内存中管理，不写入磁盘。
* *SPIFFE CSI Driver* — 将 SVID（`tls.crt`、`tls.key`、`bundle.crt`）作为只读 volume 挂载到 Pod 中。
====

.扩展阅读：传统 Pod 如何通过证书实现加密通信？
[%collapsible]
====
理解传统方案的局限，有助于体会 SPIFFE/SPIRE 解决的根本问题。

*传统流程（以 cert-manager + mTLS 为例）：*

. *生成证书*：管理员或 CI/CD 流水线使用 cert-manager 等工具，为每个服务生成证书和私钥（`tls.crt` + `tls.key`），以及共享的 CA 根证书（`ca.crt`）
. *存储为 Kubernetes Secret*：将证书和私钥存入 `kubernetes.io/tls` 类型的 Secret（etcd 默认明文存储）
. *挂载到 Pod*：Deployment 通过 volume 将 Secret 挂载到 Pod 文件系统（如 `/etc/tls/`）
. *服务配置 TLS*：服务进程启动时读取文件，配置 TLS 侦听（Nginx `ssl_certificate`、Go `tls.LoadX509KeyPair` 等）
. *建立 mTLS*：服务 A 调用服务 B 时，双方出示各自证书，用共享 CA 根证书互相验证

*主要局限：*

[cols="1,2",options="header"]
|===
| 挑战 | 说明

| 证书与工作负载身份解耦
| 证书绑定到 CN 或 DNS SAN，不绑定到"哪个 Kubernetes 工作负载"——持有证书文件的任何进程都可冒充该服务

| 证书轮换代价高
| cert-manager 可自动续期，但加载新证书通常需要重启 Pod，或实现复杂的热加载逻辑

| 私钥暴露面广
| 私钥以文件形式存在于 etcd（Secret）和 Pod 文件系统，存在被快照、备份或误读取的风险

| 规模化困难
| N 个服务 × M 个环境 = 大量独立证书需要跟踪有效期、手动更新挂载配置
|===

*cert-manager 解决了什么，还剩什么问题：*

cert-manager 能自动申请、续期、存储证书（需要配置 Issuer / ClusterIssuer），比纯手工管理进步很多。但与 SPIFFE/SPIRE 相比仍有本质差距：

[cols="1,2,2",options="header"]
|===
| 维度 | cert-manager | SPIFFE/SPIRE

| 身份来源
| 管理员预先配置（"这个 Deployment 向这个 Issuer 申请这个域名的证书"）
| 运行时从工作负载属性动态派生（namespace + ServiceAccount = 工作负载身份）

| 证书格式
| 标准 X.509（CN / DNS SAN）
| X.509-SVID（SPIFFE URI SAN = `spiffe://<trust-domain>/ns/.../sa/...`）

| 每个服务是否需要预配置
| ✅ 必须声明 `Certificate` CR
| ❌ 只需一条 `SpiffeClusterSPIFFEID` 选择器，不需要逐服务配置

| 跨平台（VM / 裸机）
| 复杂，需要额外集成
| 原生支持（SPIRE Agent 多种 attestation 机制）

| 外部 Issuer 依赖
| 必须（Vault、Let's Encrypt 或自建 CA）
| 无——SPIRE Server 本身就是信任域内的 CA

| 轮换无需重启
| 需要额外配置（cert-manager CSI driver + 应用热加载）
| 原生支持，CSI Driver 原地更新文件，应用无感知
|===

[NOTE]
====
cert-manager 和 SPIFFE 并不互斥——`cert-manager-csi-driver-spiffe` 项目可以用 cert-manager 作为 SPIRE SVID 的签发后端，适合已有 cert-manager 基础设施的团队。
====

*SPIFFE/SPIRE 改变的是什么：*

SPIFFE 不替换 TLS 协议本身，而是改变了"谁有资格获得证书"的决策机制——从"谁持有 Secret 文件"或"谁向 Issuer 申请了这个名字的证书"变为"谁是这个经过 Workload Attestation 的 Kubernetes 工作负载"。私钥在内存中生成，有效期缩短到 1 小时，原地轮换无需重启 Pod。
====

== 技术背景

SPIRE 的工作负载注册流程：

. 管理员（或 GitOps）创建 `SpiffeClusterSPIFFEID` CR，指定匹配的 namespace 和 ServiceAccount
. SPIRE Server 记录注册条目
. 当匹配的 Pod 运行时，SPIRE Agent 通过 Workload Attestation 验证 Pod 身份
. Agent 向 SPIRE Server 申请 SVID，Server 签发并返回
. SpiffeCSIDriver 将 SVID 写入 Pod 的 volume 挂载点，每小时自动轮换

== 学习目标

* 创建 SpiffeClusterSPIFFEID 注册条目
* 验证 X.509-SVID 成功挂载到 Pod
* 用 openssl 检查 SVID 的 SPIFFE URI SAN 和有效期

== 练习 1：设置你的命名空间变量

[source,bash,role="execute",subs="attributes+"]
----
NS=$(oc whoami)-{lab_ns_suffix}
echo "操作命名空间：$NS"
----

Expected result：打印 `操作命名空间：userN-{lab_ns_suffix}`。// UNVERIFIED

== 练习 2：部署测试工作负载

部署一个挂载了 SPIFFE CSI volume 的测试 Pod：

[source,bash,role="execute",subs="attributes+"]
----
cat <<'EOF' | oc apply -n "$NS" -f -
apiVersion: v1
kind: ServiceAccount
metadata:
  name: spiffe-demo-sa
---
apiVersion: v1
kind: Pod
metadata:
  name: spiffe-demo
  labels:
    app: spiffe-demo
spec:
  serviceAccountName: spiffe-demo-sa
  containers:
  - name: demo
    image: registry.redhat.io/ubi9/ubi-minimal:latest
    command: ["sleep", "infinity"]
    volumeMounts:
    - name: spiffe-svid
      mountPath: /run/spiffe/tls
      readOnly: true
  volumes:
  - name: spiffe-svid
    csi:
      driver: csi.spiffe.io
      readOnly: true
EOF
----

Expected result：`serviceaccount/spiffe-demo-sa created` 和 `pod/spiffe-demo created`。// UNVERIFIED

[source,bash,role="execute",subs="attributes+"]
----
oc wait pod spiffe-demo -n "$NS" --for=condition=Ready --timeout=60s
----

Expected result：`pod/spiffe-demo condition met`。// UNVERIFIED

== 练习 3：注册工作负载（负向控制在前）

在注册前，确认 SVID 证书文件尚不存在：

[source,bash,role="execute",subs="attributes+"]
----
oc exec -n "$NS" spiffe-demo -- ls /run/spiffe/tls/
----

Expected result：
----
spire-agent.sock
----
`spire-agent.sock` 是 SPIRE Agent 的 Workload API Unix socket，CSI volume 挂载时始终存在。但 SVID 证书文件（`tls.crt`、`tls.key`、`bundle.crt`）此时**尚不存在**——没有匹配的 ClusterSPIFFEID 注册条目，Agent 不会颁发 SVID。这是本练习的负向控制：身份不会自动分配，必须显式注册。

现在创建 SpiffeClusterSPIFFEID 注册条目：

[source,bash,role="execute",subs="attributes+"]
----
cat <<EOF | oc apply -f -
apiVersion: spire.spiffe.io/v1alpha1
kind: ClusterSPIFFEID
metadata:
  name: $(oc whoami)-demo
spec:
  spiffeIDTemplate: "spiffe://{trust_domain}/ns/{{ .PodMeta.Namespace }}/sa/{{ .PodSpec.ServiceAccountName }}"
  podSelector:
    matchLabels:
      app: spiffe-demo
  namespaceSelector:
    matchLabels:
      kubernetes.io/metadata.name: "$NS"
  ttl: 3600s
EOF
----

Expected result：`clusterspiffeid.spire.spiffe.io/userN-demo created`。// UNVERIFIED

== 练习 4：验证 X.509-SVID 已挂载

等待 CSI Driver 颁发并挂载 SVID（通常 10-30 秒）：

[source,bash,role="execute",subs="attributes+"]
----
oc exec -n "$NS" spiffe-demo -- ls -la /run/spiffe/tls/
----

Expected result：
----
tls.crt  tls.key  bundle.crt
----
三个文件证明 SPIRE Agent 已完成 Workload Attestation，SVID 成功颁发并通过 CSI Driver 挂载。// UNVERIFIED

== 练习 5：检查 SVID 证书结构

[source,bash,role="execute",subs="attributes+"]
----
oc exec -n "$NS" spiffe-demo -- \
  openssl x509 -in /run/spiffe/tls/tls.crt -text -noout | \
  grep -A3 "Subject Alternative Name"
----

Expected result：
----
        X509v3 Subject Alternative Name:
            URI:spiffe://{trust_domain}/ns/<你的命名空间>/sa/spiffe-demo-sa
----
SAN 字段中的 SPIFFE URI 就是这个工作负载的唯一身份标识。有效期由 SpireServer 的 `defaultX509Validity`（1 小时）控制。// UNVERIFIED

In short: SVID 的 SAN = 工作负载的身份证号。凭此证书，任何 mTLS 对端都可以验证"谁在连接我"。

== 证据检查点

* 注册前和注册后 `/run/spiffe/tls/` 的内容分别是什么？这说明了什么？
* SVID 的 SAN 字段格式是什么？其中哪些部分来自 SpiffeClusterSPIFFEID 模板？
* 为什么私钥（`tls.key`）可以安全地放在 Pod 文件系统里？

.参考答案
[%collapsible]
====
* 注册前为空（无 SVID），注册后有三个文件——证明 SPIRE 采用显式注册模型，未注册的工作负载不会获得身份。
* SAN 格式：`spiffe://<trust-domain>/ns/<namespace>/sa/<serviceaccount>`。Namespace 和 ServiceAccount 来自模板变量。
* 私钥由 SPIRE Agent 在内存中管理后写入 tmpfs（内存文件系统），不持久化到磁盘；CSI volume 挂载点的内容在 Pod 结束时自动清理。
====
