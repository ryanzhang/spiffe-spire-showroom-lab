= SPIFFE/SPIRE 零信任工作负载身份实验
:navtitle: 简介

通过 Red Hat Zero Trust Workload Identity Manager Operator，在 OpenShift 上为微服务和虚拟机工作负载构建可验证的加密身份体系。

== 本实验研究什么

传统的服务间认证依赖 IP 地址白名单，或将证书和私钥静态存储在 Kubernetes Secret 中——证书一旦泄漏就是长期威胁，轮换需要重启 Pod。

本实验展示如何用 *SPIFFE/SPIRE* 的零信任工作负载身份体系替代上述方案：

* 每个工作负载获得加密签名的 *SVID*（SPIFFE Verifiable Identity Document）
* SVID 由 SPIRE Server 基于工作负载的 Kubernetes 元数据（namespace + ServiceAccount）实时派生并签发，有效期短，原地自动轮换，无需重启 Pod
* 服务间 mTLS 不再依赖任何静态证书或手工密钥管理
* 信任边界可跨越 Kubernetes 和虚拟机

== 你将完成的任务

. 观察 SPIRE Server、Agent 和 CSI Driver 的运行状态，理解各组件职责
. 为存量应用三步接入 SPIFFE：ConfigMap → ClusterSPIFFEID → 更新 Deployment
. 验证基于 SVID 的 mTLS 通信：正向通过，负向拒绝
. 使用 OpenShift Service Mesh 为 Spring Boot 微服务透明启用 SPIFFE mTLS（零代码改动）
. 使用 JWT-SVID 作为 Bearer Token 对 REST API 进行认证
. 在 KubeVirt VM 上部署 SPIRE Agent，对 PostgreSQL 建立 mTLS 数据库连接

== 学习目标

* 说明 SPIFFE ID、SVID、Trust Bundle、Trust Domain 的含义和关系
* 使用 SpiffeClusterSPIFFEID 注册工作负载并验证 SVID 颁发
* 构建基于 SPIRE 的 mTLS 微服务通信，并演示负向控制
* 理解 JWT-SVID 在 REST API 认证中的作用
* 将 SPIRE 信任域扩展到非 Kubernetes 虚拟机工作负载

== 本实验不能证明什么

[cols="1,2",options="header"]
|===
| 常见误解 | 实际边界

| SPIRE 替代网络隔离
| SPIRE 提供身份层；你仍然需要 NetworkPolicy 控制流量路径

| JWT-SVID 适合所有场景
| JWT-SVID 适合短连接 HTTP API；长连接数据库和 gRPC 更适合 X.509-SVID

| X.509-SVID 与传统证书没有区别
| 传统证书是静态的、手工管理的；X.509-SVID 由 SPIRE 基于工作负载身份实时派生、原地轮换，私钥从不持久化到磁盘

| 本实验覆盖联邦信任域
| 跨 trust domain 联邦（Federation）不在本实验范围内

| SPIFFE CSI Driver 是独有的文件挂载技术
| 文件挂载本身不是 SPIFFE 独创（K8s Secrets Store CSI Driver 也做到）；SPIFFE 独有的是身份从工作负载属性动态派生 + 原地短周期轮换 + SVID 格式（URI SAN）
|===
